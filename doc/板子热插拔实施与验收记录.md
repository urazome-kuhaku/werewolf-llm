## 执行契约

1. 解释器读取不可变观察并输出类型化候选批结果，不直接修改 `GameState`。
2. 技能、角色和动作名称只用于数据绑定；执行内核不能按名称调用专属处理器。
3. 冻结包同时绑定知识说明、有效能力、动作注册表、执行计划及身份摘要。已开始的局不再读取仓库全局动作定义。
4. 同时结算组先收集伤害、保护、治疗及死亡前替代，再确认最终死亡，死亡后触发只消费确认事实。
5. 成本、历史和资源在成功提交边界写入；失败、取消、PASS 的行为由显式策略决定。重试和恢复不得重复扣费。
6. `GameManager` 在串行锁内重核 revision、已接受请求、来源和派生授权范围，再原子替换状态；不能通过放开目标校验实现连带效果。
7. 公开结果和私密结果使用明确的接收者、字段和披露时点；不把权威状态或未公告死亡直接传给脚本玩家。
8. 白天插入、多步选择和触发队列必须保存游标及恢复点。循环或预算耗尽时停在可审计错误边界，不丢弃触发后继续判胜。

补充的 A 语义约定：`ON_SUCCESS` 表示合法接受并执行，保护抵消伤害不撤销此次使用；`ON_EFFECT` 才要求效果实际生效。默认 PASS 不扣成本，收费必须显式设置。全局 PASS 由宿主绑定当前窗口内的技能实例，内部请求仍使用该技能的规范动作编码；配置的 `pass_effects` 可以清空守护历史或产生明确声明的事实，普通伤害效果不会因为 PASS 执行。

历史 schema 1 的纯知识包保留原有人工提交 `ActionResolution` 的兼容范围。它不因此获得自动解释执行能力；新的自动开局入口必须有冻结执行计划和动作注册表。老板子 schema 1 的自动兼容计划由固定版本转换器从原冻结资料恢复，不能在恢复时读实时全局动作表。
