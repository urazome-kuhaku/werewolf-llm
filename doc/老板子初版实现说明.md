# 老板子初版实现说明

## 范围

本说明对应 `classic_12_seer_witch_hunter_idiot@1.0.0` 候选板，也就是 12 人预女猎白：4 狼、4 民、预言家、女巫、猎人、白痴各 1 人。板子采用屠边胜利；女巫首夜与后续夜晚按冻结规则使用解药和毒药，只有解药尚可用且板子有效规则允许时才会在狼刀确认后看到当晚刀口；猎人只在板子允许的狼刀或放逐出局窗口触发，被毒死不触发；白痴只在放逐窗口以 `AUTOMATIC` 方式翻牌存活并失去投票资格。

候选板的来源是：

```text
vault/_workbench/official_12_20260928/draft/boards/classic_12_seer_witch_hunter_idiot/1.0.0/board.md
```

它当前保留 `CANDIDATE_PENDING_HUMAN_REVIEW` 状态。准备和联调使用独立 preview 编译包，不等同于正式发布。

屠边的角色分组直接来自冻结板子的 `board.victory.role_groups`，胜负评估使用这份规则数据，不根据运行时的 `team=good` 或其他主持器临时分类推断。

## 运行时边界

主持器 `GameManager` 是唯一的状态提交者。每个座位有独立的 `PlayerRuntime` session，当前生产实现有两种，另有一个测试工具：

- `PiRuntime`：通过 Pi RPC 子进程运行，使用 loopback 知识网关和座位 bearer token；
- `DemoRuntime`：生产 `play run` 在 `runtime: scripted` 座位使用的确定性 harness，通过同一个本局 loopback 知识网关读取该座位知识和技能状态；
- `ScriptedRuntime`：低层协议测试工具，不是 `play run` 的生产脚本运行时。

每局只启动一个 loopback 知识网关；网关为每个座位签发不同 token。每个座位仍有独立的 session 标识、会话目录和 runtime 进程，不能用另一个座位的 token 或知识上下文。

运行时收到的是绑定了 `game_id`、座位、session epoch、phase、观察增量和行动窗口的 `TurnRequest`。响应先经过协议、身份、窗口、目标和资源校验，再由 manager 的串行提交路径写入事件。Pi 端知识读取、角色卡、公共事件和 `get_skill_status` 都按座位隔离。

Pi 默认配置约定是 `github-copilot/gpt-6-luna`。配置可切换 provider、model、reasoning 和 `runtime.pi` 的 executable、版本、自动压缩、自动重试，但本轮验收不使用其他模型。

## 白天与夜晚

白天由 day coordinator 和主持器 shell 共同推进。首日且板子启用警长时，竞选边界先于首夜死亡公告建立；候选发言、投票和必要的 PK 完成后移交警徽，`complete_sheriff_transfer` 实际进入 `DAY_SPEECH`。随后先用 `day announce` 提交死亡公告，再完成适用的警徽移交和遗言，最后才打开普通白天发言队列。后续阶段依次处理顺序发言、投票收集、平票、明确放逐或无人放逐、放逐后的触发窗口、遗言和胜负检查。放逐不会由投票收集器直接改变玩家生命状态，必须经过 board-derived exile decision 的 serialized commit。

夜晚由 night coordinator 建立板子定义的狼队讨论、夜间行动和结算边界。狼刀、预言家查验、女巫资源和触发技能使用板子冻结的 action contract；老板子额外有 `classic_resolution` 作为有界主持端适配器。它只负责老板子当前所需的行动组合，不是任意新板子的通用规则解释器。

### 遗言

遗言不是普通存活玩家的 `DAY_SPEECH` 队列。`LastWordsFlow` 从当前轮次的夜间 resolution provenance 或当前放逐 vote window 识别资格，并拒绝历史轮次、错误死因、普通发言队列和未授权座位。遗言请求使用 `last-words` logical label，其观察摘要明确说明这是遗言机会；超时后可针对同一物理请求 retry，成功的 public speech correlation 和 `LAST_WORDS_COMPLETE` 审计共同用于去重和恢复。

### 触发技能

角色能力先以知识库中的 trigger grant 和 effective rules 表达，再在身份、事件、发动窗口和消耗状态满足时建立 `TRIGGER_ACTION`。玩家选择型能力由主持器发出私密提醒，对应座位运行时查询自己的技能状态并决定发动或 PASS；主持器提交前重新校验 grant、目标和当前窗口。白痴的放逐触发在板子中标记为 `AUTOMATIC`，由主持器按规则自动翻牌存活并移除投票权，不等待白痴提交玩家选择。猎人的玩家选择与白痴的自动效果都通过板子赋予的 trigger event/effect/window 字段表达，不应散落成主持器中的角色名分支。

## 启动入口

使用 CPython 3.11 和 `uv`。先在本机完成 Pi 安装和 `github-copilot` provider 登录，再确认 `pi --version` 属于 `0.87.x`。每次实验都使用必须尚不存在的新输出目录；不要复用上一局的 `game.yaml`、active game 或 session。Pi 登录后的默认配置是 provider `github-copilot`、model `gpt-6-luna`、reasoning `medium`。

当前环境的只读 `pi doctor` 诊断已记录 executable、version、version-compatible 通过，Pi 版本为 `0.87.1`；`auth: skipped_no_reauth` 仅表示诊断没有重复认证，不能作为 provider 登录、额度或真实对局可用的证明。

```powershell
uv sync --locked
$pi3Dir = ".runtime/classic-pi3-" + (Get-Date -Format "yyyyMMdd-HHmmssfff")
uv run werewolf play init --output $pi3Dir --pi-seats 1,2,3 --provider github-copilot --model gpt-6-luna --reasoning medium
uv run werewolf play run --config "$pi3Dir\game.yaml" --experimental-preview --max-rounds 20
```

要进行四 Pi 实测，另起一个全新目录，将 `--pi-seats` 改为 `1,2,3,4`；其余座位由 `DemoRuntime` 脚本 harness 接管。不要在同一目录中先后运行 3 Pi 和 4 Pi：

```powershell
$pi4Dir = ".runtime/classic-pi4-" + (Get-Date -Format "yyyyMMdd-HHmmssfff")
uv run werewolf play init --output $pi4Dir --pi-seats 1,2,3,4 --provider github-copilot --model gpt-6-luna --reasoning medium
uv run werewolf play run --config "$pi4Dir\game.yaml" --experimental-preview --max-rounds 20
```

做离线脚本入口检查时也使用新目录：

```powershell
$scriptDir = ".runtime/classic-scripted-" + (Get-Date -Format "yyyyMMdd-HHmmssfff")
uv run werewolf play init --output $scriptDir --all-scripted
uv run werewolf play run --config "$scriptDir\game.yaml" --experimental-preview --max-rounds 20
```

若需逐步观察主持器：

```powershell
uv run werewolf moderator --config "$pi3Dir\game.yaml" --experimental-preview
```

手动主持不要把所有命令拼成一段脚本；`status` 用于确认当前队列和边界，不能替代固定顺序。老板子候选的合法顺序是：

1. 建局：`new` → `next` → `next` → `start`；在 `PLAYER_PREPARE` 中反复 `prepare status` / `prepare next [seat]`，全部 ready 后执行顶层 `next`。
2. 每夜：`night open` → 反复 `night team next`（失败用 `night team retry`，需要新一轮时用 `night team again`）→ `night advance` → `night open` → 反复 `night action next [seat]`（失败用 retry）→ `night advance` → `night open` → `night auto-resolve` 或 `night resolve <json-file>`。自动结算只处理已提交并通过协议校验的请求，不打开窗口、不补交缺失行动。
3. 夜间结算后，若为 `TRIGGER_ACTION`，执行 `trigger open` → `trigger pending`；对每个玩家选择请求反复执行 `trigger next/retry [seat]`，请求全部提交后再执行一次 `trigger resolve <json-file>` 或板子支持的 `trigger auto-resolve`，最后 `trigger finish`。自动触发没有玩家请求时也要先推进空请求队列，再执行 resolver。夜间来源的 `trigger finish` 回到 `DAY_ANNOUNCE`；随后执行 `victory night-check`，只有 `ONGOING` 才继续白天。若无触发窗口，结算后直接执行 `victory night-check`。
4. 首日警长：`victory night-check` 为 `ONGOING` 后先 `sheriff start <candidate...>`，再完成 `sheriff speech`、`sheriff vote` 和必要 PK，最后 `sheriff transfer`。竞选在死亡公告之前；helper 计算的合法候选可以包括本首夜已有死亡 provenance 但尚未公告的死者。`sheriff transfer` 实际进入 `DAY_SPEECH`；随后先执行 `day announce` 提交死亡公告，再完成必要 badge 和遗言，最后才 `day speech open` 打开普通白天发言。
5. 普通白天：`day announce` → 反复 `last-words status` / `last-words next [seat]` → `day speech open` / `day speech next/retry` / `day speech close` → `day vote open` / `day vote next/retry [seat]` / `day vote collect` / `day vote confirm`。平票时改走 `day pk speech ...` 与 `day pk vote ...`。
6. 白天放逐：`day confirm-exile <seat|none>` 后，若出现 `TRIGGER_ACTION`，先 `trigger open`，再用 `trigger next/retry` 提交所有玩家请求（自动触发则推进空请求队列），然后执行一次 `trigger resolve <json-file>` 或 `trigger auto-resolve`；之后处理 `last-words`，再按需完成 `sheriff badge open` → `next` → `resolve` → `finish`。badge 完成会关闭这个白天边界并进入 `VICTORY_CHECK`，没有 badge 时才执行 `trigger finish` 进入 `VICTORY_CHECK`，随后执行 `victory check`。若没有 trigger，先处理遗言，再按需完成 badge，没有 badge 时执行 `day finish`，随后 `victory check`。白天来源的 trigger 必须遵守“触发结算 → 遗言 → badge（如需）→ 胜负”的顺序；badge guard 不能阻止已经提交的死亡公告。
7. `victory check` 返回 `ONGOING` 时自动进入下一夜的 `NIGHT_TEAM_CHAT`，不需要顶层 `next`；胜利时进入 `FINISHED`，执行 `finish` 生成归档。`save` 只创建一致边界 snapshot，不能代替 `finish`。

完整命令条件见仓库根目录 README 的“人工主持模式”。

输出目录的 `games/active/<game_id>/` 保存运行中的 private projection、冻结 ruleset 和已生成的 snapshots；成功 `play run` 的最终 JSON 行包含 `winner`、`run_status=CLOSED`、`archive_id`、`archive_path` 和 `snapshot_id`，归档位于 `games/archive/<timestamp>_<game_id>/`。将最终输出中的 `archive_path` 传给 `uv run werewolf archive verify "<archive_path>"`，完成 manifest、hash、schema 和可见性校验。失败发生在一致边界之前时可能没有新的 snapshot，也不会自动 resume；已有 active 数据和一致 snapshot 应保留用于排查。`runtime.pi.compatible_version` 是可选非空标记，例如 `0.87.x`。

## 最近修复摘要

- `prepare`、串行发言、行动和投票四类 flow 共用包含 `request_id` 等字段的严格响应 JSON Schema，避免响应只能靠隐式字段解析。
- 归档从 active 游戏根目录精确排除 `.runtime` 临时 session 目录，不排除 active 根目录本身；`archive verify` 拒绝归档根目录的 `.runtime` 等未知路径，避免把身份提示、模型上下文或 token 带入不可变归档。
- `TRIGGER_ACTION` 按夜间/白天来源分流：夜间 `trigger finish` 回到 `DAY_ANNOUNCE`，白天再按遗言、badge 和 victory 顺序推进。本轮没有新增角色专属分支。
- `finish` 失败时只允许从 `FINISHED`、无活动请求且无 pending 的边界回滚；内部审计事件为 `FINISH_ROLLBACK`，`command finish` 可恢复到合法的 `READY`/`RUNNING` 状态。
