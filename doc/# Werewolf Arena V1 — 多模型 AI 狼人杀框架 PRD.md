# Werewolf Arena V1 — 多模型 AI 狼人杀框架 PRD

> 文档状态：**V1 开发基线（2026-09-27 反向评审通过）**  
> 版本：v1.0  
> 归档日期：2026-09-27  
> 优先语言：CPython 3.11；Pi Extension 允许最少量 TypeScript  
> 产品形态：本地无 UI 的 CLI / 主持人控制台；不对外提供在线服务  
> 术语：**主持人 / GM** 指控制游戏的 Python 主进程及其真人操作员；**玩家 / Agent** 指一个独立 Harness 会话。

## 0. 执行摘要与决策记录

### 0.1 产品定位

构建一个由 **Python 主进程统一主持、多个独立 AI 玩家参与** 的本地狼人杀实验框架。每个玩家可独立配置模型与 Harness；V1 **只实现 Pi RPC 适配器**，同时保留扩展 Claude Agent SDK、Codex 或 Direct API 的接口。

项目的差异化能力不是让模型背诵预置规则，而是：**玩家在获得身份后，能够根据实际需要主动检索 Obsidian 规则知识库，自行理解当前板子、角色及特殊交互，并在持续会话中完成发言、投票和技能决策。**

V1 不追求完整自动裁判。Python 负责调度、消息权限、基础合法性校验与记录；复杂的技能生效判定由真人主持人确认。模型只做玩家决策，不读取或修改权威游戏状态，也不直接写任何对局文件。

### 0.2 已确认的产品决策

| ID | 决策 | V1 结论 |
|---|---|---|
| D-01 | 项目形态 | 独立本地游戏工程，**不是**仅面向外部 Harness 的独立 Skill 产品 |
| D-02 | 主控 | Python 单主进程，统一调度游戏及所有信息流 |
| D-03 | 玩家 Harness | V1 采用 Pi **RPC 子进程**；保留可配置 `PlayerRuntime` 适配接口 |
| D-04 | 模型 | 各座位独立配置模型、提供商、推理参数和预算；同局允许混合 |
| D-05 | 知识库 | Obsidian Vault 存储板子、角色、机制、规则版本及来源；提供从板子名联网调研并生成知识草稿的入库流程 |
| D-06 | 检索 | **必须保留游戏内自主动态查询**；Skill 指导查询，受控只读工具实际访问已发布 Vault 快照；联网检索仅用于开局前的知识生产 |
| D-07 | 文件权限 | Harness 无权写权威状态、公共发言或其他玩家笔记；Python 是唯一写入者 |
| D-08 | 消息 | 公共频道、狼队私聊、个人私信均由 Python 进行权限分发 |
| D-09 | 白天发言 | **按座位/当前板子规则串行**执行；上一位完成后才启动下一位 |
| D-10 | 投票和技能 | 使用统一编号的结构化行动；投票视为公共行动的一类，普通发言不算技能 |
| D-11 | 裁定 | Python 做最小身份/窗口/目标合法性检查，复杂技能效果由真人主持人裁定 |
| D-12 | 记录 | `state.json` + 可读 `public.md`；内存中调度，按游戏轮次/约定边界正式保存 |
| D-13 | 时间控制 | 可配置软超时友好提醒、硬超时停止推进并交由主持人处理 |
| D-14 | V1 暂缓 | 数据库、UI、完整自动规则引擎、多个 Harness 同时实现、向量数据库、精确中途崩溃恢复 |

> **需要区别**：Obsidian / Werewolf Skill 提供“知识访问方法与行为指引”；Pi Extension 提供可执行的、可审计的只读规则查询工具。Skill 本身不是持久会话管理器，也不是规则裁判。

## 1. 项目目标、用户与成功标准

### 1.1 目标

1. 从 CLI 创建一局游戏，选择规则板子、座位数量、各玩家的 Harness 和模型配置。
2. 按规则分配身份；每位 AI 拥有独立、贯穿本局的会话，不会因一次发言或投票结束而丢失身份。
3. 玩家开局自行查询当前板子和自己的角色；需要时可继续查询其他角色及特殊交互。
4. 主进程按阶段分发**仅该玩家有权查看的信息**，串行管理公共发言，支持授权狼队私聊。
5. 玩家以结构化协议返回发言或行动；Python 收集、校验并由主持人完成复杂裁定。
6. 生成可读的公开对局 Markdown 和可供下次运行读取的 JSON 游戏状态。
7. 不改变游戏主流程，即可在后续增加新的 Harness 适配器。

### 1.2 使用者

- **真人主持人 / 开发者**：创建房间、选择板子、配置模型、观察日志、确认技能结算与推进流程。
- **AI 玩家**：通过自身持续会话接收信息、主动检索知识、推理、发言和提交行动。
- **后续实验使用者**：在同一板子下比较不同模型的规则检索与游戏行为（非 V1 的完整评测平台）。

### 1.3 V1 成功定义

在一份经过人工确认的规则快照下，可以运行一场由 Pi 驱动的本地 AI 对局演示：玩家能够自主检索、独立保持身份、持续多轮串行发言、参与隔离的狼队讨论、提交投票和夜间技能请求；主持人可以完成结算，并得到一致的对局日志。**首个工程验收允许先用 2～3 个真实模型配合脚本玩家**，不要求首个迭代即稳定完成十二个 AI 的全自动长局。

## 2. 范围边界

| 类别 | V1 必须实现（P0） | 可简化 / 视时间安排（P1） | 暂不实现（P2 / 后续） |
|---|---|---|---|
| 游戏主控 | Python CLI、阶段调度、主持人操作 | 暂停、延长、重试及人工纠错 | 网页 UI、在线联机房间 |
| Harness | Pi RPC、模型/玩家配置、独立会话 | 统一上下文统计 | Claude Code、Codex、Direct API 适配器 |
| 知识 | 根据板子名联网调研、多来源取证、规则草稿生成与人工发布；Obsidian 读取、游戏内主动检索 | 来源权重、版本冲突和自动刷新增强 | Embedding、向量数据库、对局中联网补规则 |
| 玩法 | 首个固定版本板子、公开发言、投票、夜间窗口、狼队讨论 | 触发类技能、更多板子 | 全量角色库、完整自动裁判 |
| 数据 | JSON 游戏状态、公共 Markdown、独立 Pi Session | 私人笔记、临时阶段检查点 | SQLite、事件服务、复杂数据分析平台 |
| 安全 | 不给玩家读权威状态或写文件能力，隔离私密消息 | 进程级目录隔离加固 | 面向不受信任插件的强沙箱平台 |

**非目标**：V1 不提供供任意外部 Harness 独立运行的通用狼人杀服务，也不要求自动判定所有特殊技能的生效先后；这些由后续扩展接口和主持人解决。

## 3. 概念与职责边界

### 3.1 组件

| 组件 | 负责 | 明确不负责 |
|---|---|---|
| `GameManager` | 房间、阶段、顺序、行动窗口、有效结果提交、轮次结束 | 推导 AI 玩家策略 |
| `ModeratorCLI` | 真人主持操作、人工确认与纠错、暂停/继续 | 冒充玩家生成投票（除非独立配置真人玩家） |
| `PlayerSessionManager` | 按玩家启动/复用/终止 Session、超时和消息同步 | 根据规则擅自判定技能效果 |
| `PlayerRuntime` | 统一 `start / send / steer / abort / close` 语义 | 保存全局权威状态 |
| `PiRuntime` | Python 管理 Pi RPC 子进程、处理命令和事件、维持独立会话 | 直接修改对局 Markdown |
| `RulesetWorkbench` | 根据板子名联网调研、提取主张、分析变体/冲突并生成知识草稿 | 直接发布未验证规则或访问对局秘密 |
| `KnowledgePublisher` | 验证板子/角色/机制/交互的完整性，发布不可变知识版本并编译索引 | 在进行中的对局里修改规则快照 |
| `KnowledgeService` | 从固定规则快照受控查询板子、有效角色、机制、交互和阅读计划 | 查询真实玩家身份与秘密行动 |
| `KnowledgeExtension` | Pi 内注册只读游戏规则工具，向 Python 查询 | 持有完整游戏状态或任意文件访问能力 |
| `WerewolfReadingSkill` | 指导玩家开局必读、按阶段查询和遗忘后重读 | 保存规则权威副本或完成游戏裁判 |
| `MessageRouter` | 将事件按 PUBLIC / TEAM / PRIVATE / GM 权限分发 | 让玩家自行指定任意接收群体 |
| `ActionValidator` | 核对行为码、角色授权、阶段、基本参数及重复提交 | 完整判定特殊技能相互作用 |
| `Referee` | 主持人对复杂生效、公开内容、结算冲突进行确认 | 替玩家制定战术 |
| `GameFileStore` | 内存状态导出 JSON、由公开事件生成 Markdown | 让多个 Harness 并发读写同一文件 |

### 3.2 并发策略

- 每名 AI 是**一个独立会话实例**，并不意味着一个固定 Python 线程。由 Python `asyncio` 负责等待 RPC I/O、调度和超时。
- Pi V1 可以采用每玩家一个独立 Pi RPC 子进程与独立持久 Session；实现资源占用统计，未来可优化按需启动。
- **白天发言与狼队讨论串行**：完成且通过验证才进入下一位。
- **秘密投票或相互独立的夜间操作可并发收集**，但是否并发必须服从当前板子的行动依赖和信息可见性。
- Python 内存中的权威游戏状态单写入；Harness 仅返回响应，不拥有写文件权限。

## 4. 完整对局主流程

### 4.1 状态与阶段

建议状态标签（具体首夜/白天先后由板子决定）：

`CREATED → RULESET_READY → ASSIGNED → PLAYER_PREPARE → [NIGHT_TEAM_CHAT → NIGHT_ACTION → NIGHT_RESOLVE → DAY_ANNOUNCE → DAY_SPEECH → VOTE → DAY_RESOLVE → VICTORY_CHECK] × N → FINISHED`

允许主持人在阶段边界执行 `PAUSED`、`RETRY_PLAYER`、`MANUAL_RESOLVE`。禁止仅凭 AI 文本自行切换阶段。

### 4.2 流程明细

| 步骤 | 主进程执行 | AI 玩家执行 | 完成条件 |
|---|---|---|---|
| 1. 创建本局 | 选板子版本、导入规则快照、校验人数/身份、读取玩家配置 | 无 | 配置与规则校验通过 |
| 2. 分配身份 | 随机分配并锁定真实身份、关联每个座位 | 无 | 人数、角色数量一致 |
| 3. 启动玩家 | 创建独立 Pi Session、注入公共 System 和专属身份信息 | 接收专属信息 | 所需 Session 可调用 |
| 4. 开局自主学习 | 告知板子 ID、角色 ID，提供规则工具，不直接灌入全部 Vault | 主动查询板子/本人角色，按需查询机制和交互 | `get_board` 与本人 `get_role` 的最低检索要求完成；玩家返回 ready |
| 5. 夜间狼队讨论 | 仅向有资格的狼人打开 TEAM 频道，安排串行讨论 | 狼人依次读取增量队友消息、提出意见 | 规定的讨论轮次完成 |
| 6. 夜间行动 | 根据当前板子打开有资格角色的行动窗口 | 各玩家按需查询规则后提交编号行动或放弃 | 所有必需窗口完成或主持人处理超时 |
| 7. 夜间裁定 | 先基础合法性校验；展示行动给主持人；记录真实结算和可见反馈 | 仅收到有权知道的行动反馈 | 主持人确认夜间结算 |
| 8. 白天公告 | 公布允许公开的死亡/事件结果并记录公屏 | 接收新增公开信息 | 公告提交完成 |
| 9. 依次发言 | 按板子顺序仅激活一位；传递其未见公开及授权私信 | 发言前按需查规则，自行生成本次发言 | 当前玩家发言完成且被记录，才轮下一位 |
| 10. 投票 | 根据公开/秘密投票规则分发投票请求，收集结构化行动 | 结合本轮信息独立提交 `VOTE` / 合法弃票 | 全部具备投票权者完成或超时处理 |
| 11. 白天裁定 | 统计合法票、处理平票/出局/遗言/触发技能（复杂部分主持人确认） | 若获得触发行动窗口，再自主决定是否发动 | 阶段结算确认并发布许可内容 |
| 12. 下一阶段 | 检查是否终局，刷新内存与轮次快照；否则继续 | 保持各自会话和身份 | 主持人推进或游戏结束 |

> **业务边界**：真人主持人可直接输入、纠正或批准**结算结果**，但 AI 玩家投票与技能选择仍应由其自行产生；真人自己要下场玩时，应另设 `HumanRuntime`（后续）。

### 4.3 消息路由与同步

1. 游戏消息由 Python 生成 `event_id`、可见范围、阶段及序号；**不允许模型自行伪造来源与可见范围**。
2. 每个玩家持有独立已读游标，获取自身有权查看、尚未交付的新消息。公开发言写入内存公屏，随后才允许下一个玩家开始。
3. 私有技能请求、夜间行动和未公开投票不得提前同步到公共频道；主持人确认后，再生成相应的公开/私有结果事件。
4. 为避免误把投递当作完成，只有当前任务最终成功处理后才确认相应增量已读；失败时允许去重重送。
5. `public.md` 是对局记录展示副本，而非 Harness 的共享可写通信总线；更新公共历史和实时消息首先发生在 Python 内存中。

## 5. 核心需求详述

### FR-01 本局配置与初始化（P0）

- 输入：本局 ID、板子 ID/版本、随机种子（可选）、人数、玩家列表、座位/模型/提供商/Harness、主持模式、时间预算。
- 同一局允许模型混合；V1 实际受支持 Harness 仅 `pi`，遇到其它类型应明确报不支持，而非静默降级。
- 真人主持人选择采用的人数、身份组成及所需规则特例，执行开始前校验；游戏中冻结规则快照。
- 验收：非法人数、重复座位、不存在模型配置、规则缺项均有可理解报错；启动成功后身份数量无误。

### FR-02 Pi 持久玩家会话（P0）

- 每个座位独立 Pi RPC 进程或严格独立的 Session，严禁多个玩家共用一个对话上下文。
- 初始化时注入全局行为边界和该座位身份；后续发言、投票、技能窗口仅发送本次阶段要求、新增信息、必要的简短身份/技能状态提醒。
- `PlayerRuntime` 建议接口：`start(config, initial_context)`、`run_turn(observation, request)`、`steer(message)`、`abort()`、`close()`；附加 `get_session_ref()` 仅用于快照关联。
- Pi RPC 命令使用唯一请求 ID；**`prompt` 被接受不是任务完成**。需要继续消费事件直至当前任务 settle，解析最终输出并完成校验。
- 不采用无持久会话的启动参数；实际 session 位置按各玩家独立配置。
- 验收：一位玩家可完成规则学习→发言→投票→下一轮发言，保持身份和已有上下文，不重复初始化。

### FR-03 Obsidian 知识与自主检索（P0）

- **游戏内必须提供动态查询**，不能退化成 Python 预先将全部规则一次性注入。
- 知识库是一级子系统，至少包含：板子介绍和总流程、角色技能和限制、公共机制、特殊交互、术语、来源证据、阅读计划和知识测试。
- Obsidian Vault 分为隔离工作区、正式发布区和可重建运行索引；正式区至少组织为 `boards/`、`roles/`、`mechanics/`、`interactions/`、`glossary/`、`sources/`、`tests/`；Markdown 使用必要的 YAML Frontmatter，包含 ID、名称、别名、版本、适用板子、来源及审核标识。
- “Obsidian Vault”在 V1 中指 Obsidian 兼容的普通目录和 Markdown 文件格式；安装 Obsidian 客户端不是开发、编译、查询或运行游戏的前置条件。
- 当前对局引用冻结的**规则快照**；维护中的 Vault 更新不应改变同一局的中途裁定口径。
- 开局向每位玩家发送知识启动卡，包含当前板子和本人角色的 ID、名称、简要介绍、快照引用及必读清单；启动卡不是完整规则灌入。
- 开局最低要求：每位玩家必须调用 `get_board` 和自己的 `get_role` 后才可 ready；`get_role` 返回基础角色叠加当前板子差异后的有效角色规则。更多检索由模型决定。
- 游戏中任意允许决策的窗口仍可调用规则工具；模型遗忘、没看明白或遇到特殊交互时，应重新读取而不是凭训练记忆猜测。
- 查询接口至少包括：`get_board`、`get_role`、`get_mechanic`、`get_interaction`、`get_rule_topic`、`search_rules`；由 Python 确保结果限定当前 Ruleset Snapshot，返回稳定引用、适用版本、正文、来源和推荐后续阅读。
- Werewolf Skill 负责解释何时检索、如何处理缺失/冲突、不可将攻略当硬性规则；现有 Obsidian Skills 可辅助**知识编写/格式**，但不是游戏内授权检索的唯一实现。
- Pi 内使用最小 TypeScript Extension 注册**只读专用工具**，由它请求 Python `KnowledgeService`；不向模型开放 Vault 原始路径遍历、任意文件读写或通用 Shell。
- 为避免 Skill 依赖被禁用的 Pi `read` 工具，V1 应通过可控的启动指令/显式 Skill 展开加载 Werewolf Skill；不要假设关闭 `read` 后任意 Skill 都能自动读取全部参考文件。
- 验收：未知板子/角色能正确报错；陌生板子测试中，模型能从启动卡完成板子和本人角色必读，并在后续阶段重新读取机制或交互；不能通过查询获得本局其他玩家真实身份。

### FR-03A 规则知识调研与入库（P0）

- 主持人只需提供自然语言板子名或别名，例如“预女猎白”；系统在开局前启动独立规则生产流程，不要求主持人先手工回答整套常见规则。
- 系统按板子组成、胜负条件、夜间顺序、角色能力、狼队可见性、投票/平票、遗言和特殊交互生成搜索计划，联网搜集多个独立来源。
- 每条会影响执行或裁定的规则必须形成带来源引用的原子主张；记录 URL、标题、发布者、访问时间、引用片段、内容哈希和适用版本。
- 同名板子存在不同平台、赛事或年份变体时，必须先聚类为不同候选规则集，不得把互斥规则按多数票静默拼接。
- 自动生成 `boards/`、`roles/`、`mechanics/`、`interactions/` 草稿及冲突报告、覆盖报告和知识问答测试。
- 只有来源冲突无法依据版本消解、或关键维度搜索后仍缺失时，才向主持人提出带证据和推荐项的定向问题。
- 草稿通过 Schema、引用闭合、角色数量、规则覆盖、冲突和语义测试，并由主持人查看发布 diff 后，才可写入 `status: published` 的不可变语义版本；审核人和审核时间使用独立字段记录。
- 联网调研工作区不得被游戏内 `KnowledgeService` 查询；游戏只使用已发布的冻结快照，进行中不得联网补规则。
- 验收：仅输入一个常见板子名，可以产出带多来源证据、变体/冲突说明和完整性报告的可审核知识包；缺关键规则或未处理冲突时不能发布。

### FR-04 公共发言（P0）

- 按当前板子/主持人指定的发言顺序**串行**启动；当前 Harness 结束并由主进程确认发言后，才激活下一位。
- 只给当前玩家其应见的新增事件、目前合法发言阶段信息及必要的状态摘要。
- 普通发言是 `speech`，不视为技能、不消耗技能次数；允许内容包含游戏内谎言和身份声明，但一律作为**玩家声明**，不是规则引擎事实。
- Python 把已确认的公开发言写入当前内存公屏并向后续玩家增量同步；轮次保存时渲染至 `public.md`。
- 验收：第二位发言人能看到上一位发言，第一位看不到后续发言；任一发言失败不会错误推进队列。

### FR-05 狼队私密频道（P0）

- 主进程根据真实身份和当前板子自动计算狼队频道成员；不存在由 Agent 任意输入队伍 ID 的取数能力。
- 进入狼队阶段时，**复用公共串行发言的调度逻辑**，但消息只广播给授权队友。V1 默认讨论一轮，允许主持人追加一轮。
- 狼队仍是各自独立 Pi Session；仅通过 Python 转发授权的团队发言，不共享 Session、不共享可读取的狼队文件。
- 聊天内容不进入 `public.md`；必要时仅在受保护的主持状态中保留团队消息。随后收集袭击目标偏好并按当局板子规则确定最终请求/由主持人处理分歧。
- 不允许无关玩家、被规则排除的特殊狼或游戏中失去资格者获取频道信息；成员资格以当前 Ruleset 为准。
- 验收：仅被授权的狼人收到队友消息；非狼无法通过正常 Prompt 和已暴露工具读取团队内容；异常请求被拒绝并可定位。

### FR-06 统一行为与技能协议（P0）

- 所有玩家输出统一 `PlayerResponse` 包装结构，分为 `speech` / `action` / `ready` / `error` 等 `kind`；正式行动用编号 `action_code`，发言不注册为技能。
- `kind=action` 使用 `actions[]` bundle；普通窗口只有一项，当前板子的女巫药剂窗口可原子提交救药、毒药或两者，以支持同夜双药且避免半提交。
- 行动码由项目维护的注册表定义，**编号只表示类型，不表示权限**。
- 主进程检查：当前 `request_id`/行动窗口有效、玩家身份与状态、允许阶段、剩余使用次数、目标范围、弃权是否允许、重复提交；复杂效果留给主持人。
- 特殊技能**请求 / 主持确认 / 结果通知**为三个独立概念，避免“发动”等同“成功生效”。
- 投票属于人人可用、但受阶段与资格限制的行动；实际公开与否由所选板子确定。
- 验收：无技能角色无法通过假造行动码施放其他角色技能；迟到或重复行动不改变已结算阶段。

### FR-07 夜间行动与主持裁定（P0）

- 主进程按规则开启有资格角色的窗口，可依赖前一窗口中**已裁定且可向当前玩家透露**的信息（例如某规则版本中的女巫救人信息）。
- 夜间角色只接收自己有权知道的提示与裁定反馈；狼队共享内容仅发给当局授权成员。
- 主持人界面列出合法请求及所需交互选择，裁定生效、失败、消耗与后续可见信息；Python 记录并分发。
- 白天公开事件/允许公开的技能结果进入公屏；白天发动技能**不等于其全部机制和私有细节必须公开**，最终由板子规则与主持人决定。
- 验收：至少一项个人技能和一项狼队行动完成请求→基础校验→人工裁定→正确权限分发闭环。

### FR-08 投票与后续行动（P0）

- 投票以独立结构化行动收集；秘密投票时所有玩家接收同一投票前的公共状态，不得看见其他尚未公开的票。
- Python 负责统计已校验结果，主持人确认出局、平票、遗言与触发技能等当局规则。
- 投票及白天触发动作完成后由主进程公告准许公开的信息、检查胜负并推进下一阶段。
- 验收：某玩家先提交秘密投票，不会影响其他玩家的可见上下文；统计、弃权、非法目标反馈符合当前规则。

### FR-09 超时及人工兜底（P0）

- 每次发言/行动按玩家或阶段配置**软超时**与**硬超时**；建议初值 120 秒 / 240 秒，仅为默认实验参数。
- 到达软超时若任务仍在执行，通过 Pi RPC 的 `steer` 机制追加**一次**友好提醒，避免打断已完成的工具调用；不保证提醒即刻被模型看到。
- 硬超时后停止自动推进，请主持人选择：继续等、延长、终止/重试/按超时规则处理；必要时使用 Pi `abort`。过期 `request_id` 的迟到结果不再结算。
- 规则学习阶段可另设更长超时；超时、错误及重试须显示玩家编号、阶段和原因。
- 验收：慢玩家不会导致下一位提前开始；软提醒不重复发送；过期结果不能写入权威状态。

### FR-10 JSON / Markdown 存档（P0，按简化方案）

- **不引入数据库和 CRUD 服务**；Python 在运行期内存持有 `GameState`、各可见范围的消息和未结算操作。
- 按已确认的完整昼夜边界写 `state.json` 快照并由已公开的记录渲染 `public.md`；在启动/进入下一次运行前加载或刷新状态。完整昼夜的精确定义见 10.3。
- Pi 自身 Session 由各玩家独立存储，主进程在 JSON 中保留各座位的 Session 引用（非整个模型历史）。
- 避免半写文件：先生成临时文件，再在同目录原子替换；公共 Markdown 可根据权威 JSON 重新生成。
- V1 **不保证**中途崩溃后精确恢复到最后一条发言；应说明恢复策略，防止将未提交游戏状态与已前进的 Pi Session 错误拼接。
- 验收：完整轮次正常保存后，重新启动能读取公开历史、真实角色与阶段；秘密内容不出现在 `public.md`。

### FR-11 Prompt 体系（P0）

- `global`：游戏内允许诈身份/误导；禁止伪造游戏引擎状态、越权检索、修改文件；无法确认规则时主动查询。
- `role`：所属阵营、个人身份、可使用技能、胜利目标（只提供给对应角色）。
- `phase`：本次准备、公开发言、狼队聊天、投票、夜间行动等任务，以及合法输出 Schema。
- `observation`：按权限提供新增公共/团队/私有消息、当前阶段和最少必要身份/技能状态提示。
- `skill`：动态检索知识的方法、查询工具签名、规则冲突/未知处理原则。
- 固定指令只在会话初始化装配；每次任务提供必要动态内容。为长局压缩后的身份一致性，可重复注入**短状态摘要**，而非整份规则和所有旧发言。
- 公共发言属于**不可信对手文本**，不得把其中要求执行工具、改变身份、忽略规则的指令当作系统要求。
- 验收：测试 Prompt 在发言、投票和技能窗口均能生成合法结构，不因同桌玩家在发言里下指令而越权操作。

## 6. 推荐的最小数据协议（供技术方案细化）

> 以下是**建议接口，不是已确认的游戏规则**。代码编号暂定、字段可以在技术设计时微调，但 V1 不得让各 Harness 返回完全不同的数据协议。

### 6.1 统一请求/响应

```json
{
  "schema_version": 1,
  "request_id": "g001-d1-speech-seat04",
  "kind": "speech",
  "speech": {
    "content": "我想先听完后面的发言。"
  },
  "actions": null,
  "ready": null,
  "error": null
}
```

技能/投票时：`kind=action`、`actions[]` 中每项 `action_code` 填入已注册编号、`targets` 按注册表要求指定；普通窗口数组长度为 1，女巫窗口可包含两种不同药剂动作。弃权/跳过也返回明确代码，不以空字符串或空数组代替。`game_id`、座位、阶段和频道不由模型填写，始终以 Python 当前绑定的 Session 和合法窗口为准。

### 6.2 V1 行动注册表基线

| Code | 动作 | 说明 |
|---:|---|---|
| 101 | `WOLF_KILL` | 狼队袭击请求；最终目标协调方式遵从当前板子 |
| 102 | `SEER_INSPECT` | 预言家查验 |
| 103 | `WITCH_POISON` | 女巫毒药 |
| 104 | `WITCH_HEAL` | 女巫救治 |
| 105 | `HUNTER_SHOOT` | 符合触发条件的猎人开枪 |
| 201 | `VOTE` | 当前拥有投票资格的玩家使用的公共行动 |
| 202 | `ABSTAIN` | 仅当前规则允许弃票时可用 |
| 299 | `PASS` | 当前行动窗口允许不发动时使用；是否开放按窗口定义 |

### 6.3 消息事件结构

```json
{
  "event_id": 27,
  "round_id": 1,
  "phase": "NIGHT_TEAM_CHAT",
  "kind": "speech",
  "speaker": 3,
  "channel": "TEAM",
  "audience": [1, 3, 7, 10],
  "payload": { "content": "我建议优先考虑 5 号。" }
}
```

`audience` 由 Python 计算，不由模型决定。至少支持 `PUBLIC`、`TEAM`、`PRIVATE`、`GM_ONLY`。真实身份、夜间未公开行动、投票详情和主持人裁定中间数据不能无条件进入公共视图。

### 6.4 玩家配置示意

```yaml
game:
  board_id: classic_12_seer_witch_hunter_idiot
  board_version: 1.0.0
  moderator_mode: human_assisted
  soft_timeout_seconds: 120
  hard_timeout_seconds: 240

players:
  - seat: 1
    harness: pi
    provider: provider_a
    model: model_a
    reasoning: medium
    session_dir: .runtime/players/seat_01
  - seat: 2
    harness: pi
    provider: provider_b
    model: model_b
    reasoning: high
    session_dir: .runtime/players/seat_02
```

配置不包含 API 密钥明文；密钥通过本机环境变量或提供商推荐的安全凭证机制获取。其余座位配置按相同规则扩展。

## 7. 狼队私聊专项方案

### 7.1 V1 最小协议

1. 夜间阶段开始，GameManager 根据权威真实身份、存活状态和当局特殊规则生成**授权成员名单**。
2. `MessageRouter` 创建本夜逻辑 `TEAM` 频道（内存对象即可），不生成任何供 Agent 自行读取的共享文件。
3. 主进程按既定顺序激活狼人，每人仅收到本轮截至其行动时已发生的授权狼队消息。
4. 每名狼人返回 `speech`；主进程确认并广播给后续授权狼队玩家。
5. 默认讨论一轮；主持人可追加一轮。正式刀人请求由各狼或代表按当局配置提交；分歧时由真人主持人根据所选规则处理。
6. 狼队阶段结束后关闭本次讨论窗口；将团队消息仅存于受控的主持状态（必要时生成不提供给玩家的 GM 记录）。

### 7.2 防窥屏要求

- 不向 Agent 暴露工作目录中的完整游戏状态，也不让 Pi 的普通文件查询工具读取项目运行目录。
- 使用**最小工具集**：游戏中模型只需要规则查询工具；日常模型回复由 RPC 返回给主进程，无需通用 Bash/文件写工具。
- Agent 无权指定其他玩家 ID 或任意频道作为消息检索目标；主进程只负责推送当前玩家已授权的信息。
- Pi Extension 与进程运行在同一操作系统权限下，**关闭普通工具≠真正沙箱**。V1 仅加载可信自研 Extension，并确保工具端不返回隐私状态；未来如允许不可信扩展，增加独立 OS 用户/容器。
- 对阵营频道编写正向与反向测试：授权成员能交流，非授权成员无论从正常工具、Prompt 注入还是配置越权请求都不能获取团队数据。

## 8. CLI / 主持人交互清单

V1 使用命令式 CLI 或逐步菜单，不需要 GUI。至少支持：

- `new`：配置本局及模型座位；选择规则版本，校验身份分配。
- `start`：启动 Pi 玩家，派发身份与开局规则学习任务。
- `status`：展示当前阶段、发言队列、等待玩家、行动窗口与错误状态；真实身份仅主持人可见。
- `next` / `confirm`：推进已完成阶段、确认裁定，不能跳过未完成的必需动作。
- `resolve`：选择技能实际效果、消耗和允许公开的通知内容。
- `extend` / `retry` / `abort`：处理异常或超时玩家；每次记录主持人干预原因。
- `save` / `finish`：按完整昼夜边界保存或结束游戏，生成 `public.md`；仅在无未决裁定和提交临界区时允许手动 `save`。

**原则**：主持人可以知道全部隐藏信息，但这些内容不得随着 CLI 输出重定向、调试日志或公共记录传递给普通 AI 玩家。

## 10. 保存边界、异常与恢复策略

### 10.1 当前约定

- 游戏进行时，**Python 内存是当前阶段的权威工作状态**。
- 每名 Pi 的对话历史由其自身独立 Session 维护；主进程不每次重新发送全部公开历史，仅发送新增信息。
- `public.md` 由 Python 基于已正式公开的对局记录生成；`state.json` 保存真实角色、技能状态、轮次与授权消息等全局状态。
- 正常情况下，**按一次约定的完整游戏轮次边界**正式刷新状态文件，而非每条操作都写盘。可以提供明确的手动 `save` 动作，但应避免在尚未裁定的技能中间提交不一致快照。

### 10.2 V1 异常取舍

- Python 进程/机器异常中断后，V1 不承诺精确恢复到最后一条发言。
- 必须检测 `state.json` 的保存轮次与 Pi Session 进度是否可能不同步；**不能**把已经前进的 Session 强行接在落后的游戏存档上并默默继续。
- 默认由主持人选择：从上次一致快照重新建会话（重新提供该玩家已知公开/私有信息）或放弃当前局；并明确记录这次恢复使实验数据不可视为完全连续。
- 未来确有需要再加轻量 JSONL 暂存日志/阶段检查点，不以 V1 的恢复问题为由引入数据库。
- 存档时采用先写临时文件、再同目录原子替换；保留必要错误提示，公共 Markdown 可以由确认的权威快照重建。

### 10.3 已确认的保存边界

“每一轮”固定指一个完整昼夜循环：从某夜开始，到对应白天的胜负检查完成。每个完整昼夜自动生成一致快照；整局结束后再生成以 UTC 时间戳命名的最终归档目录。允许主持人在无未决裁定和提交临界区时手动保存。V1 接受边界内异常退出可能丢失进度，不承诺逐事件恢复。

## 15. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| R-01 自主检索效果不足 | 模型读错规则或跳过必要规则 | 开局 `get_board` + 本人 `get_role` 为最低约束；增加规则查询测试集 |
| R-02 Pi 长会话上下文增长 | 成本、延迟与历史遗忘 | 增量投递、短状态提醒；观察压缩行为，限制单次工具调用次数 |
| R-03 玩家借公屏 Prompt 注入 | 越权检索、泄露信息或擅自改指令 | 强制提示词区分系统任务与对手发言；工具端彻底禁止敏感数据查询 |
| R-04 狼队私聊泄漏 | 游戏公平性失效 | Python 单点分发，禁用通用文件访问；隔离 Session 和团队成员名单 |
| R-05 人工主持差异 | 不同实验结果不可完全直接比较 | 裁定与人工干预留痕；同一对照实验固定板子和主持规则 |
| R-06 Pi Extension 权限过大 | 本机文件或密钥误暴露 | 仅加载可信最小 Extension；必要时提高进程权限隔离 |
| R-07 轮次保存与 Session 不同步 | 崩溃后错误恢复 | 明示 V1 恢复限制，记录会话引用和快照版本；异常交主持人裁定 |
| R-08 不同模型行动耗时差异大 | 串行发言拖慢整局 | 每玩家/阶段软硬超时、可配置最大步骤、友好提醒与主持人干预 |
| R-09 规则含多个民间版本 | 技能结算争议 | 首版只选择一个经过人工确认的规则版本，冻结当前局快照 |
| R-10 目标膨胀 | 假期项目无法交付 | M1 知识+M2 持续会话优先；M3 最小主持，自动裁判和多 Harness 延后 |
| R-11 联网规则来源冲突或错误 | 生成混合版本或错误规则，污染后续对局 | 原子主张带引用、版本聚类、关键项交叉验证、发布门禁与主持人确认；游戏禁止读取草稿 |
| R-12 网页 Prompt 注入 | 调研 Agent 被网页内容诱导越权执行或发布 | 网页内容始终作为不可信证据，抓取限权，提取与发布权限分离，发布必须人工确认 |

## 16. 推荐开发顺序与里程碑

| 里程碑 | 主要交付 | 阶段演示 / 退出条件 |
|---|---|---|
| **M0** 需求冻结 | 首板子、状态 Schema、权限矩阵与行动编号 | 能用规则文件解释所有首局流程与权限 |
| **M1** 知识 PoC | 调研工作台 + Markdown Vault + 编译索引 + Python 查询 + Reading Skill + Pi Extension | 只给板子名可生成待审知识包；模型可开局必读并在游戏中重读，拒绝未知或不授权请求 |
| **M2** 会话 PoC | Python `PlayerRuntime` + Pi RPC + Prompt/超时 | 同玩家跨发言、投票、下一轮连续工作，独立 Session 无混线 |
| **M3** 游戏闭环 | Python 主持/串行公屏/狼队频道/行动窗口/投票 | 在主持辅助下完成一轮关键游戏流程 |
| **M4** 存档验收 | JSON 快照、公开 Markdown、场景测试与使用文档 | 能演示一场受控对局并产出可审计文件 |

**任务优先级约束**：如果假期时间不足，先保证 **M1 + M2** 形成可演示的“动态查知识 + 持续会话”能力，暂时用脚本替代完整对局状态机；不要为了抢先做全量特殊角色牺牲核心能力。
